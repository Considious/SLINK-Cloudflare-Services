# Public Fair Fight backup — testing only

## Plan and boundaries

FFScouter remains primary. Clients capture only existing successful get-stats/get-targets responses, extracting `available_estimates.bss`, or top-level `source=bss`. Premium/faction spy values are never substituted for public BSS. Missing timestamps/BSS or unknown source are skipped, not guessed. No crawler, new Torn request, key donation, automatic settings restore, full-client database sync or chat badge is introduced. Saved chat follow-up: extension `docs/FF-CHAT-FOLLOWUP.md`.

Records are `{player_id,bs_estimate,bss_public,source:'ffscouter-bss',ff_last_updated,slink_observed_at}`. Shared records never contain observer-relative FF, keys, tokens, private stats or spy fields. FF is derived locally as `1 + (8/3) * targetBSS / observerBSS` only when SLINK already has an authenticated local score bound to the current account. Otherwise FF is N/A; never derive private BSS from a community total. Existing module safety ceilings still apply. Backup labels include the true FF source age rather than pretending the lookup time is the estimate time.

## Client behavior

- Shared extension core / identical early PDA source fragment. Dedicated `slink-ff-public-backup-v1` IndexedDB stores `records`, `pending`, `meta`; it does not touch existing data/settings stores or Chrome storage.local quota. No IndexedDB means a temporary in-memory degradation, not deletion/migration of user data.
- Upsert only a newer public timestamp. One pending record per ID, bounded near 2,000 entries; old useful cached estimates are not age-deleted. Successful backup downloads are cached but never re-contributed.
- Upload at 100 pending rows or one hour since the queue began. Max 200 records/request, 15-minute attempt spacing and five attempts/day/client. Only matching acknowledged timestamps leave the queue; failed uploads retain it. There is no shutdown send, crawler or extra timer: normal lookup activity/explicit engine flush drives work. Idle/suspended PDA does not upload. Extension's existing caller activity gates remain; a previously started passive upload can finish.
- Reuse a currently valid existing access session only—never authenticate or fetch private Torn stats just for backup. Source hooks cover ordinary client get-stats requests (War, Leveling/refinement, Bounties and any future shared caller) and passive get-targets capture. They do not intercept unrelated external scripts or secretly crawl server-side Mugging pools. Server-side-only raw results not delivered to a client are outside this collector.
- Current successful FFScouter rows always win. On provider failure or a requested player with no usable estimate, use local records first, then batch only locally missing IDs. A healthy response with every requested estimate causes zero backup lookups. A genuine missing estimate is not counted as an outage. Positive records and 10-minute negative results persist. Backup network errors cool down ten minutes, without marking failures as confirmed missing.
- Three failures within 60 seconds open a three-minute provider circuit; 429 respects a bounded longer Retry-After. One half-open probe is allowed; success resets it. Invalid/revoked credentials remain authentication errors, not a hidden outage. The existing error/cached/N/A handling survives when neither source works. Primary five-second/backup four-second deadlines bound waiting. Cache failures cannot replace a successful primary result with an error.

## Backend routes and migration

Module: `fair-fight-backup.js`, called from the existing contribution worker before its existing routes. Uses existing signed permission-session verification, with existing FF-related/chat scopes or admin.*. No new key/scopes needed. A signed session proves a SLINK account, not cryptographic provider origin; an authorized malicious client can still lie. Strict whitelist/positive ranges/future timestamp bounds, per-user limits and a shared conservative budget mitigate but do not eliminate poisoning. No attestation or additional provider validation crawl is claimed.

- POST `/api/fair-fight/backup/contribute`: 1–200 records, 64 KiB streamed body ceiling, dedupe newest per ID, indexed pre-read, conditional JSON-array SQL upsert using one JSON bind. Older/equal timestamps do not update estimate rows; concurrent races remain protected by the SQL WHERE clause. ACK covers records already known/newer too.
- POST `/api/fair-fight/backup/lookup`: 1–200 requested IDs, one primary-key-indexed query, compact records only. No full-table response or R2 access.
- GET `/api/fair-fight/backup/status`: admin.* only, on-demand COUNT/MAX and latest snapshot metadata. COUNT scans the table; not a client polling endpoint.
- Migration `permissions/migrations/0022-fair-fight-public-backup.sql` creates the public estimate table, atomic daily quota reservations and snapshot metadata. No production schema was changed by this work. Apply to a TEST database before a TEST deployment.

Defaults: `FF_BACKUP_ENABLED=false`, `FF_BACKUP_DAILY_ROWS=20000` (newer candidate rows reserved globally/day; hard maximum 50,000), `FF_BACKUP_SNAPSHOTS=false`, `FF_BACKUP_SNAPSHOT_HOURS=24`. Each signed user can submit up to 1,000 candidate rows/day. Reservation costs can be consumed by duplicates/failed writes; this is deliberately conservative and never bypassed with an automatic retry. Ordinary clients retain unsent queues after 429. Quotas are not a guarantee that the rest of the account has sufficient free allocation.

## R2 disaster snapshots

Snapshots run in the separate tiny `snapshot-worker.js`, not in the contribution worker's live requests or existing collection cron. `wrangler.snapshot-test.jsonc` is an explicitly disabled test template: replace its test D1 ID and create/bind a private test R2 bucket; do not deploy the placeholder or point it at production unintentionally. The existing contribution worker keeps its existing D1/R2 configuration and cron unchanged apart from disabled feature vars.

The optional snapshot worker's hourly trigger performs work only for a new configurable 12–168-hour slot (24 default). A lease prevents repeating a full export for the same slot. Keyset-read pages of 1,000 rows, compact tuples `[player_id,bs_estimate,bss_public,ff_last_updated]`, gzip and a dated `fair-fight-backups/YYYY-MM-DD-HH.json.gz` object. Compression must be buffered to give R2 a known-length body; the compressed object ceiling is 32 MiB. No complete snapshot is sent to browsers. Metadata is updated only after a successful put; prefix-isolated cleanup removes snapshots older than 14 days and old quota rows. No existing user backups/mugging data prefix is touched. A failed export leaves the previous snapshot intact and does not affect lookup/contribution traffic. Snapshot data is a paged recovery copy, not a transactionally frozen D1 point-in-time export. Restore is an explicit administrative operation using the same conditional-newer upsert; no automatic client/cloud restore.

CPU/memory limits still apply to large full snapshots, particularly Workers Free. Paged reads follow stream backpressure; exports abort above 64 MiB uncompressed or 32 MiB compressed rather than building unbounded buffers. Aborted exports never publish a partial snapshot. Gzip ultimately buffers bounded compressed bytes; Cloudflare runtime scale/CPU acceptance must be measured in staging. Do not promise a 100,000-row snapshot fits 10 ms of free CPU. For larger scale, use chunked snapshot continuation or a separately budgeted execution environment; not silently upgrade/spend.

## Deployment status / compatibility

Source/testing branch only. No Worker deployed, D1 migration executed, R2 bucket created, production secrets changed or main branch updated. Clients keep their existing contribution-service origin; until these routes are deliberately deployed to that service, missing/disabled routes fail gracefully with local cache still useful. A fully isolated external test deployment requires a separately configured client origin and matching existing session-signing secrets; those are NOT invented or deployed here. Local end-to-end tests use the same route/core code and SQLite/IndexedDB, not a claim of live Cloudflare readiness. Physical PDA/native bridge and actual Cloudflare limits remain acceptance items.

## Expected usage (incremental, assumptions not guarantees)

100 active users each encountering 500 new/timestamp-changed public estimates/day, deduped locally, with 100–200 records/upload: roughly 300–500 Worker upload attempts/day. Spread-out activity or two devices can increase attempts; each client caps at five/day. Browser CORS preflights may add an OPTIONS request per uncached preflight. Raw submissions could reach 50,000 rows/day; the default global reservation admits at most 20,000 newer candidates/day. Excess stays queued. At most those admitted rows are upsert candidates; duplicates/SQL races can lower actual changes. Batching reduces requests/transactions, NOT D1's per-row billing.

Normal complete FFScouter responses: zero backup lookup requests. Upload D1 reads include one indexed pre-read per submitted ID, quota primary-key reads/writes and upsert conflict checks, typically tens of thousands to low hundreds of thousands of row reads at that example scale. Estimate writes are <=20,000/day plus quota overhead (roughly a few control writes per upload, and insertion of daily user/global counters). There is no index on updated_at, avoiding extra index-update writes. D1 metering is authoritative; verify actual rows_read/rows_written during staging.

Outage example per user: 100 targets, 67 local → one 33-ID lookup, about 33 indexed estimate-row reads. 28 returned estimates persist locally; five misses are negative-cached ten minutes. The next visit within that TTL needs no Worker lookup for these IDs. Auth validates HMAC locally, not via another Worker/Torn call.

At N shared rows, daily snapshot adds approximately N D1 row reads, ~ceil(N/1000)+small-control database statements, one R2 put/day, periodic prefix list/deletes, plus 24 very small scheduled invocations/day. A 100,000-row public catalog likely occupies tens of MB including D1 overhead; measure actual database and gzip sizes. Fourteen snapshots retained. No R2 GET on normal contribution/lookup paths.

Published Cloudflare Free allowances checked 29 October 2026: Workers 100,000 requests/day; D1 5 million rows read/day and 100,000 rows written/day with 5 GB total free storage; R2 Standard 10 GB-month, 1 million Class A and 10 million Class B operations/month. These allocations are shared with existing services and do not establish the account's remaining allowance. A paid Workers subscription is not required by this source design, but zero incremental cost cannot be guaranteed without account metrics, real CPU testing and overall consumption. No paid plan or service was enabled.
